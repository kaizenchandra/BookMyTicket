# ADR 092: Immutable accepted payment-attempt observations

FE:BKG-03 and BE:BKG-13 are advanced by retaining newly accepted attempt-state observations in the existing customer payment history. This does not reconstruct prior transitions or claim a complete provider event log.

Migration 071 gives attempts random public timeline UUIDs and creates Payments-owned immutable observation records. A persistence trigger records an initial insert or an actual persisted state change in the same transaction as the attempt write. It records previous/new state, amount, currency, private provider association and authoritative database recording time. Updates that retain the same state do not emit records. Existing observation guards remain unchanged: duplicate polls and ignored stale regressions create no extra history. Rollback removes both the attempted write and its observation. No old state is backfilled as a newly occurred event.

The Payments history adapter unions these observations with durable capture/recovery records before applying the existing twenty-item cursor pagination. Public kinds are attempt_created, attempt_authorized, attempt_captured, attempt_refunded and attempt_failed. Each includes a random attemptId for grouping; non-attempt records return null. Provider references and private previous-state storage remain excluded. Existing capture/recovery cursors remain valid. The same owner-authorized Bookings orchestration and no-store behavior apply.

The frontend says Attempt observed as …, displays the safe attempt reference and records newest first. It distinguishes accepted observations from provider processing chronology, capture observation from booking confirmation, and refunded observation from a complete booking refund ledger. Earlier missing observations and disruption/refund-ledger limitations remain explicit.

Tests drive the actual PostgresCollection.observe writer: six duplicate concurrent inserts, accepted transitions, stale created/failed/captured observations, association mismatch, immutable rows, transaction rollback, stable grouping, twenty-plus-five pages and provider redaction. These supplement existing reconciliation/booking correctness tests. No live provider API behavior is changed or inferred as verified. Historical reconstruction, refund/disruption timelines, retention, browser/accessibility/load acceptance remain open.
