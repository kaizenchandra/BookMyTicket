# ADR 102: Flight supplier administration; external integration blocked

FR-05 introduces a travel product into a movie/event/sports modular monolith. No flight supplier, API contract or sandbox credentials were provided. Do not reuse cinema seat inventory, fabricate fares/PNRs, or represent payment capture as a flight confirmation. Complete flight fulfillment remains blocked pending the supplier contract.

A Flights module owns persisted supplier profiles (stable unique code, name, airline IATA codes, environment, draft/suspended status) and versioned INR commercial rules. The administrative UI and APIs support searching, pagination, editing, audit and exact arithmetic preview. No credentials or arbitrary remote URLs are accepted. Profiles cannot be activated for sale: an actual adapter and its operational readiness checks are required first. Integration availability is explicitly not configured, not healthy with zero errors.

The application layer coordinates store ports and Reporting's public audit contract. The PostgreSQL adapter owns only flights tables and uses Identity's authorization contract. Reads/writes require flights.read and fresh MFA at the HTTP boundary. Profile mutations also require flights.manage; commercial mutations and preview require pricing. These grants are assignable by existing access administrators; migration 076 grants them to nobody. It expands the role permission constraint without changing assigned roles.

Create idempotency locks actor/key, fingerprints the normalized request and persists the response in the same transaction as supplier creation/audit. Stable unique supplier code prevents later duplicate creation. Edits lock the supplier and reject stale versions. Commercial rules have independent versions; absent rule uses expectedVersion 0. Rule and profile before/after states are audited atomically. Failed audit rolls back changes.

Preview applies a basis-point markup to supplied base fare only, rounds half up to paise, passes supplied tax through and adds the configured fixed service fee. Amounts use bigint and serialize as decimal strings. This is configuration arithmetic, not a supplier quote, tax engine, commission calculation, checkout or guarantee of availability. Additional fee tax/commission policies await business and supplier agreements.

Required next work after supplier selection: verify official API documentation; implement authenticated supplier adapter and normalized fare/ancillary contracts; revalidation; supplier reservation and ticketing state machines; durable reconciliation of unknown outcomes; disruption synchronization and incident workflows; supplier-specific cancel/void/refund integration and booking/payment compensation. This requires distinct flight booking ownership and explicit integration with the existing payment module. No full FR-05 completion is claimed.
