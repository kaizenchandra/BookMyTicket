# ADR 034 — Customer inbox notices for staff replies

Support owns the decision that a customer-visible staff reply was recorded. It publishes support.staff_replied through Reporting's DurableEvents contract within the message/case/audit/command transaction. Internal notes and customer-authored replies do not publish this event. Identical keyed retries return before publishing, so one committed staff message produces one outbox record. Failed transactions roll back the event with the message. Headerless callers retain existing reply/version semantics.

The v1 payload contains ownerId and messageId; aggregate_id is the case UUID. It contains no subject, message body, contact information or credentials. Notifications recognizes this event using the existing customer-inbox-v1 consumer. Delivery and acknowledgment are atomic, event-ID uniqueness deduplicates repeats, and the existing bounded retry/backoff/dead-letter/replay flow applies. No external email/SMS is sent. Delivery may be delayed; a notice reports a past reply, never a current case-state guarantee, and does not reopen or mutate the case.

The inbox links to /cases?caseId=<UUID>. The case-list API accepts an optional validated caseId and always scopes it to the authenticated owner. Exact selection works independently of the existing newest-100 list limit. Foreign or absent IDs return an empty owned result, and the UI shows unavailable. Message access independently checks ownership and excludes internal notes. The selected-case page links back to all cases and does not show the create form.

Existing messages are not backfilled and retrying an already saved old command does not synthesize a new event. No migration or new secret is needed. Deploy app and worker together to enable publication and consumption. Event/schema and case-query contracts are updated. Browser interaction and accessibility acceptance remain open; staff assignment notifications, reply email/SMS, delivery badges, customer case pagination and broader support scope remain outstanding.
