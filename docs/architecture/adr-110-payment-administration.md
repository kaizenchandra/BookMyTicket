# ADR 110: Payment observations, finance detail and approved exports

FR-13 extends the existing Razorpay implementation; it does not introduce another gateway or move money. PaymentAdministration uses a PaymentAdminStore application port with a PostgreSQL adapter. Identity authorizes finance access; Reporting audits reads/exports. Queries stay in Payments-owned tables. Bookings are linked by UUID without reading private booking tables.

Payment transaction IDs are now intentionally visible to finance-authorized staff and searchable exactly, alongside internal attempt IDs, provider, method, state, booking and observation-date ranges. This changes the earlier minimal finance projection; refund directory and customer payment-history privacy remain unchanged. Cursor scopes bind actor and filters; filtering precedes pagination. Reads and approved report generation use repeatable-read transactions.

Provider observations retain only normalized method and bounded technical error codes/reasons; email, contact, card, VPA, free-text error descriptions and notes are not copied into these records. Metadata follows the official Razorpay payment entity documentation: https://github.com/razorpay/markdown-docs/blob/master/api/payments/fetch-all-payments.md (checked during implementation). Unknown/unavailable method/refunded amount stays null, not invented. Cumulative refunded paise only increases across observations; captured/refunded states retain the existing anti-regression rules. Invalid optional refund amounts are ignored rather than changing the authoritative payment amount. Migration 084 extends immutable observation history for changes to state/method/error/refunded amount; old records are not backfilled.

Finance detail distinguishes original payment value, provider-observed refunded amount, local capture, recovery obligation, provider-order reconciliation and unconnected bank settlement. Historical failure codes may persist after success; the timeline supplies context. Merchant auto-capture remains the configured strategy; no manual/partial capture is implemented. Refund eligibility remains unknown until policy/approval/provider workflows exist. No refund action is falsely represented as available.

The exceptions queue includes provider orders with unknown/failed mapping, review_required or reconciliation errors, even without a payment attempt. It shows worker failures, last check and review flags. This is payment-status reconciliation, not provider settlement/bank matching. It does not override review blocks or retry leases.

CSV export requires current finance access/MFA, an explicit reason/approval, an increasing observation-date range of at most 366 days and at most 5000 matching rows. It exports all matching rows, not only a visible page, or rejects oversized selections; there is no silent truncation. Amounts remain integer paise. Cells are quoted and formula prefixes neutralized. Authorization/query/audit occur in the same transaction and an audit failure prevents delivery. Approval means the requesting finance actor's explicit approval, not a separate two-person approval policy. Reports are delivered directly without durable file storage or scheduled delivery.

Existing server-created orders, signed callback/webhook verification, durable deduplication/reconciliation, captured-payment fulfillment, balanced collection entries and late-capture recovery remain in force. Real merchant API/webhook verification is still unperformed. Refund execution/idempotency, additional wallet/gateway adapters, bank-settlement reconciliation and manual/partial capture remain incomplete. Browser acceptance is unverified.
