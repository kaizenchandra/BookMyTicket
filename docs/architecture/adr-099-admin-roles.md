# ADR 099: FR-03 admin users, roles and permissions

FR-03 adds persistent named role definitions, allowlisted permissions, account-role assignments, explicit admin metadata and effective grant provenance to the existing identity module. Reporting remains the owner of activity history. Five initial role definitions (Super Admin, Operations, Finance, Support and Content Manager) are created without assigning any account or widening any existing account grant. Names are case-insensitively unique.

Effective access is the union of direct platform grants and permissions from active assigned roles. Preserve existing authorization consumers by materializing this union into identity.grants. identity.admin_role_grants marks only rows inserted by role computation; pre-existing/direct rows are never marked role-derived. Recompute deletes only marked grants, then inserts missing permissions from every active role and records their provenance. Direct grant replacement followed by recomputation preserves role access; overlapping direct grants survive role edits/deactivation. Tenant/gate scoped and unrecognized platform grants are preserved. Operators must use the admin API for managed grant changes; manually overwriting derived rows bypasses provenance semantics.

All mutations acquire the existing identity administrative advisory lock, recheck active access.manage authorization, then acquire account/role row locks in deterministic order. Account and role expectedVersion checks reject stale updates. Changes update affected account versions and revoke all affected sessions within the same transaction as effective grants and audit. Self account changes and edits to any role assigned to the acting administrator are rejected, including inactive assigned roles. At least one active access manager must remain. Shared-role deactivation retains assignments but removes role-derived access; reactivation deliberately restores it and revokes sessions again.

New admin accounts use the existing email/OTP identity flow; no credentials, session or verified-contact assertion is manufactured, and no invitation is sent. Existing contacts conflict rather than silently being promoted. Creation requires actor/operation-scoped idempotency keys and stores a fingerprint/result; changed payloads conflict. Role names and account contacts provide business uniqueness beyond retry records. Login still requires email verification and protected actions require current MFA.

Directories support before-limit filtering and actor/filter-bound keyset pagination. Accounts expose masked contacts, admin display names, direct grants, assigned role IDs and effective grants. Activity includes actions performed by the account, direct target events and shared-role events whose affectedAccounts contain the account. Only explicit privilege-change fields are returned; arbitrary details from other audited actions are omitted. Role/account creation, changes and reads are audited; financial and booking modules remain unchanged.

Migration 074 owns the tables, initial definitions and metadata. New admins with no remaining access stay discoverable through is_admin, avoiding accidental disappearance after role deactivation. No account grants are seeded. Existing accounts can be appointed explicitly via exact contact/reference lookup.

Verification covers mutation authorization, duplicate creation/retry conflicts, stale versions, session revocation, role propagation, direct grant preservation, inactive assignment rejection, self/indirect-self escalation, activity, audit rollback and role pagination scope. All module import checks pass. Browser visual/interaction/accessibility acceptance remains unverified; prior browser-access host was unavailable. Named roles cover the actions actually implemented by this platform, not hypothetical travel-system capabilities.
