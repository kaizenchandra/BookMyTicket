# ADR 104: Shared room capacity, date rates and atomic allocations

Inventory owns room types, occupancy, date-level stock, rate plans/date overrides, hotel inventory allocations, request replay and inventory change history. Hotels exposes a public property-lock contract; no Inventory adapter queries Hotels tables. Hotel content remains independently owned. Existing occurrence-seat inventory is unchanged. This is a modular-monolith workflow with one transaction for each inventory mutation and no external calls in transactions.

Every operation locks the property through its owner and then the room aggregate. Room mutations, bulk writes, hold creation, consumption and release serialize on that room. This deliberately chooses simple per-room serialization rather than per-night parallelism. Capacity is one room/day pool shared across all rate plans. The authoritative count is reserved quantity plus held quantity whose expiry is later than database time, intersected against each requested night. A multi-night request validates every night before creating one allocation; any failure rolls back everything, including history/audit. Unconfigured nights are unavailable, not unlimited.

Consumption validates held state, active property/room, and expiry again in a conditional UPDATE at database time. Repeated consumption of the same reserved allocation is idempotent; released/expired allocations cannot be consumed. Release targets the immutable allocation UUID, never a room/date counter, so stale release cannot decrement a newer hold. Reserved rooms remain committed until explicit authorized release. They are inventory allocations only: no customer booking, payment, ticket or hotel confirmation is created. UI confirmation explicitly distinguishes this from a paid booking.

Ten-minute holds have no extension API. Actor/operation/key request fingerprints return the original response for identical retries and reject changed payloads. Retrying a hold returns its original ID/expiry even if it has subsequently expired/released; allocation listing supplies effective current state. Expiry needs no worker: every capacity read/consume uses database time, and the listing derives expired state without trusting cleanup. Stored held rows may therefore remain held in historical storage while effective state is expired. No delayed task can revive them.

Bulk edits replace total capacity (not incremental availability), global stop-sell/blackout and selected-plan nightly base price/discount/minimum stay for an inclusive-from/exclusive-until range of at most 366 nights. Live commitments prevent capacity reductions below used stock. Room configuration versions guard stale bulk and plan edits. Lower occupancy limits cannot invalidate live/future allocations or plan included occupancy. Existing allocations preserve accepted price/policy snapshots. Active holds may consume saved rate terms after plan edits; deactivated property/room prevents consumption.

INR nightly amount is `(date override or default base + max(0, guests − included) × extra guest) × (10000 − discountBps) / 10000`, rounded half up per room/night then multiplied by room quantity. Date prices express seasonal rules; date discounts express simple promotions, without customer segmentation or coupon stacking. Minimum stay applies to every night in the stay; all ages count toward occupancy. Stays support 1–60 nights and 1–20 rooms, with server-validated non-past IST check-in. No tax/commission/payment engine is implied. Refundability is a plan policy snapshot, not a payment refund operation.

Administrative grants are existing hotels.read/hotels.manage/pricing with fresh MFA: rate-plan writes require pricing; bulk writes require both manage and pricing; hold/allocation/reconciliation actions require manage. All mutations append immutable history and audit atomically. Reconciliation observations compare operator-reported physical capacity with configured capacity and record discrepancies without changing inventory. Corrections require an explicit reviewed bulk edit, constrained by existing commitments.

FR-BE-044 channel-manager synchronization remains blocked awaiting an authorized provider/API contract and secure sandbox configuration. No fake supplier adapter or externally authoritative stock is introduced. Supplier inventory ownership/allotment rules and reconciliation leases must be agreed before integrating a channel manager. Browser acceptance and production-scale load testing remain outstanding.
