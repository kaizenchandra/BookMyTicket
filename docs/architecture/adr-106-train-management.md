# ADR 106: Train reference catalogue and local incident administration

FR-09 requires an authorized railway booking provider for live schedules/fares/availability, booking submission, PNR/confirmation/waitlist/cancellation/refund tracking, asynchronous reconciliation and provider-specific restrictions. No provider documentation or sandbox configuration was supplied. This increment implements persistent local reference catalogue and incident workflows; supplier fields remain null and bookable=false. A local train service is not a booking or a provider-confirmed schedule.

Trains owns typed station, route and service records, stable catalogue codes, versioned edits, request replay and immutable history. Station codes are uppercase local reference identifiers, globally unique within the module and immutable after creation. Name/city/active state may change. Codes and train/class formats are local structural validation, not verified railway-provider validity.

Routes contain 2–120 ordered station calls with minute offsets (up to 7 days), boarding/alighting flags and station snapshots. The first arrival/departure offset is zero. Each subsequent arrival follows the previous departure, successive stations differ, departures do not precede arrivals, and endpoints permit boarding/alighting. Station references are validated active and locked in canonical UUID order. Routes may revisit non-consecutive stations where the local catalogue requires it.

Services have a train number, route, timezone-qualified dated departure/arrival, travel classes, optional provider-reference metadata and operational notes. Class codes must be unique; final arrival must equal the route's last arrival offset. Service save revalidates the route and current active station references, then captures current snapshots. Later station/route edits do not silently rewrite saved service schedules. These notes/constraints do not constitute supplier-specific booking-rule enforcement.

Services transition locally from planned to disrupted, resolve to planned, or withdraw terminally. Local withdrawal does not cancel a provider booking, issue refunds or notify customers. Withdrawn records remain immutable except for retained history reads. Reference station/route suspension prevents their use in new/edited schedules, without inventing external cancellation effects.

Identity owns trains.read/trains.manage platform grants, with current MFA enforced at routes and active grants rechecked transactionally. No account is automatically granted privileges. Stable kind/code and station-code uniqueness prevent duplicate catalogue records; actor/operation/key fingerprinted replay returns original create results. Edits/incidents lock the record and reject stale versions. Current state, full before/after immutable history and audit metadata commit atomically. Cross-module access uses Identity/Reporting contracts; no other module's private SQL is imported.

Directory filters run before 25-row date/UUID keyset limits and bind actor/kind/filters to cursors. Station name/code search and service train-number/route/departure-window filters support administration. History is paginated by immutable sequence. The UI shows readable station calls, IST timestamps and travel classes; live availability/fare/PNR/waitlist/cancellation/refund values explicitly remain unavailable.

Remaining FR-09 work requires the provider's official API contract, permitted booking workflow, sandbox credentials/eligibility, callback authentication/deduplication, unknown-outcome reconciliation, state separation and supplier restriction mapping. Existing movie/event/sports and hotel inventory are not used as railway sale authority. Browser acceptance and production-scale load testing remain outstanding.
