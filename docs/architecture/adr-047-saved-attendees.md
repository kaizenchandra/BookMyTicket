# ADR 047: Optional saved attendee shortcuts

FE:PRO-04 and BE:CUS-05/06 require optional storage with explicit consent. Profiles owns one versioned collection per account, containing at most ten UUID-identified name/email/phone entries. No dates of birth, IDs, emergency declarations or arbitrary registration answers are stored. Transport schemas bound and validate fields; application policy requires consent exactly when the list is nonempty and rejects duplicate identifiers.

Consent policy version 1: “I consent to storing these details in my account for reuse in future booking forms (policy version 1).” The UI explains that storage is optional, users should save only authorized details, contacts are unverified, marketing is separate, and withdrawal does not erase accepted booking records. Every accepted list revision records saved_attendees purpose, policy version, grant/withdrawal, preference version and database timestamp without attendee values. The consent checkbox resets after edits and saves.

Migration 046 adds saved_attendees and attendee_consent_history. GET/PUT /api/v1/profile/attendees authenticate the owner. Writes lock the owner row, compare expectedVersion, encrypt or clear the list and record consent atomically. Identical immediately repeated commands return the same revision without another history record; older/changed commands conflict. The existing no-store response policy applies. No PII is copied to audit metadata or browser storage.

Storage uses AES-256-GCM with a random 12-byte nonce and account-bound AAD. HKDF-SHA256 derives a distinct profiles.saved-attendees:v1 key from the configured REGISTRATION_ENCRYPTION_KEY. Ciphertext layout is nonce, encrypted JSON, then authentication tag. Existing secret-file configuration provides the root key; no new deployment secret is introduced. Account-swapped ciphertext fails closed. Missing keys block saving/reading encrypted lists; a current-version withdrawal needs no decryption and clears ciphertext. Empty lists remain readable without the key. Retained history contains no names or contacts.

Profile UI supports add/edit/remove, explicit consent, withdrawal, retry and draft-preserving conflict recovery. Checkout loads shortcuts only on request and provides an explicit selection for each name/email/phone-compatible field. It does not infer field meaning or auto-fill declarations/date/choice fields. A selection uses the existing onChange path, invalidating acceptance before review. Provider form previews do not load account shortcuts. Session-change events clear loaded shortcut lists and invalidate pending fetches; already copied form values and accepted orders are separate records. Withdrawal cannot recall already delivered page data.

Tests cover consent/limits, encryption, owner isolation, ciphertext swap, retries, conflicts, missing-key rollback, key-independent withdrawal, history privacy and suspension. Server rendering verifies explicit selection and excluded declaration/date/choice types. Full browser/keyboard/accessibility, retention/export/deletion integration, consent-policy approval for production and key rotation remain open.
