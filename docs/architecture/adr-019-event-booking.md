# ADR 019 — event catalog and booking workflow

Events owns structured organizer-facing event details: performers, organizer display name, duration, minimum-age information, genre/language, inclusions, exclusions and entry instructions. Draft creation and changes project discovery metadata through Catalog's public CategoryDrafts contract in the same database transaction. Catalog continues to own publication/moderation, versions, idempotency records and revision history. Public details require a published listing. Existing generic event listings remain supported without fabricated structured metadata.

Provider routes: GET/POST `/api/v1/organizations/:id/events`, PUT `/api/v1/organizations/:id/events/:listingId`; customer detail: GET `/api/v1/catalog/:id/events`. Mutation authentication, organization membership, draft-state/version checks and full-input idempotency fingerprints are enforced server-side. Permissions are rechecked before replay; replay cannot overwrite newer typed details. Strict schemas reject unknown fields and out-of-range durations/ages. A minimum-age display is informational; organizers can collect a required eligibility declaration through the versioned attendee form. This is not documentary age verification.

Provider UI: `/partner/venues` category editor, catalog submission, versioned venue plans, concrete sessions and attendee forms. Form preview renders the same customer fields for one admission with unsaved local preview answers. The customer journey uses `/events` → listing → venue-local session → assigned seat or general-admission quantity → reservation → immutable quote and policy acceptance → per-admission attendee registration → order → configured payment or explicitly approved zero-total confirmation → ticket wallet. Checkout displays the selected venue/date/time zone and admission count before accepting the order. Each current ticket admits one person to one session; no group/pass semantics are implied.

Inventory retains exclusive seat/capacity ownership. Event details introduce no availability counters. Existing server-authoritative sales windows, atomic holds, policy pricing, encrypted historical registrations, confirmation, QR issuance and cancellation contracts remain in use. The event catalog never confirms payments.

Verification: real PostgreSQL/HTTP tests in `tests/cinema-sports.test.ts` now include separate seated and general-admission event journeys. Both create an organization, moderate provider/listing, configure plans and two dates, reject overlap/unauthorized changes, publish a required attendee form, reject absent declarations, retain form version/answers after subsequent revisions, confirm an approved free booking, retrieve QR tickets and cancel/release capacity. Existing registration tests exercise stale forms, encrypted storage, changed retry input and missing-key rollback. Full native/container suites and deployed HTTP smoke evidence are recorded separately.

Limits: multiple concrete sessions are supported; recurring-rule generation, timed ticket-sale phases, coupled/group packages, multi-day passes, authorized online joining links, disruptions and paid refunds are still required. The existing Razorpay adapter remains the paid checkout path; this change does not verify live merchant connectivity, captures or paid event fulfillment. No event listings, paid captures or customer data are seeded into the application database. Automated fixtures remain isolated in bookmyticket_test. Browser/visual/accessibility verification is not inferred from HTTP tests.
