# ADR 097: Operator account and booking administration

The supplied `makemyticket-admin-panel.md` is an additional FRS, not proof that all 24 modules are implemented. Preserve its exact numbered IDs in `docs/requirements/admin-traceability.json`; unnumbered detailed clauses receive GAP:ADMIN module/side/ordinal IDs. Travel-specific products remain pending scope confirmation and authorized integration contracts. Existing movies/events/sports remain the operating domain.

Implement platform operator administration within the existing modular monolith. Identity owns accounts and grants; Bookings owns booking list/detail/timeline; Payments owns attempts/recovery/history; Ticketing owns fulfillment summaries. Composition passes public contracts to Bookings orchestration. No admin adapter directly reads another module's private tables. Existing financial state machines remain unchanged.

New platform grants: `access.manage`, `customers.read`, `bookings.read`. Finance screens retain `finance`. All require fresh MFA. Capabilities reveal only the current user's platform permission names and control navigation. Scoped gate/tenant grants do not authorize global records. No grants are seeded. Initial access.manage provisioning requires an authorized database operator; there is no public bootstrap endpoint.

Account changes acquire a shared administrative advisory lock before account/grant row locks, recheck active access.manage authorization, require expectedVersion and a nonempty reason, forbid self changes and protect the last active access manager. Mutation, target session revocation and before/after audit commit together. Audit failure rolls everything back. Only allowlisted platform grants can be changed; unknown and scoped grants are preserved. Version conflict rejects duplicate/concurrent updates without repeating side effects. Account status and permission changes do not restore revoked sessions. Custom role objects/invitations are not implemented; staff are existing verified accounts assigned explicit grants.

Searches use bound SQL parameters and descending timestamp/UUID keysets with full timestamp precision. Cursor scope binds actor and filters. Account lookup accepts exact reference/contact; outputs mask contacts. Bookings expose only selected historical occurrence fields, policy reference and recorded milestones. Payment/provider identifiers, arbitrary snapshots, ticket tokens and contacts are omitted. Current booking, observed payment and ticket validity states remain distinct. Payment recovery is not a completed refund.

Dashboard date presets use database transaction time with IST day boundaries. Custom dates are half-open and bounded to 366 days. GBV/bookings/cancellation drilldowns use identical booking-created cohort filters. Existing calendar month/quarter/year behavior remains compatible.

Migration 072 adds account admin versioning and directory indexes. Required verification includes revoked access, concurrent version conflicts, audit rollback, exact cursor pagination/filter scope, missing records, field redaction, provider-state separation and calendar boundaries. Full refund workflows, cancellation/rescheduling actions, supplier integrations, custom roles, geographic/product filtering, approvals, settlement and browser/load acceptance remain open.
