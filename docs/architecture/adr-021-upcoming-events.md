# ADR 021 — upcoming event discovery and local demo journeys

Catalog owns a rebuildable session projection (occurrence ID, listing ID, start time, local time zone, venue name and lifecycle state). Inventory remains authoritative for actual occurrence state, sales windows and capacity. Scheduling calls CatalogSessions.recordSession through its public contract in the same local transaction as scheduling. Migration 026 backfills existing occurrences. No capacity counters or prices are copied to the projection.

`GET /api/v1/catalog?kind=event&upcoming=true` filters on at least one open projected session with start later than database time. Filters, counts, facets and pagination use that condition; cursor fingerprints include the upcoming flag. A bounded batch query adds the nearest future session to each result. The Events page uses this filter and renders venue-local dates/venues. A future session can still be sold out or outside its sales window; the real session/seat APIs and protected reservation command decide bookability. No upcoming card authorizes a sale.

Future schedule edits/disruptions must update the projection through the same contract or a deduplicated durable consumer. Those lifecycle operations are not yet implemented; direct database changes bypass the contract and can leave discovery stale. The initial migration is a complete backfill, not evidence of a verified operational rebuild command. Booking continues to reject unavailable state from Inventory regardless of discovery state.

The user explicitly requested mock events. Extended the guarded local demo seed with four fictional structured event listings, original SVG posters, four venue plans and eight sessions. Each has one free bookable session and one paid display session protected by the demo payment guard. Seated and general-admission plans, explicit free commercial policies, required attendee names and eligibility declarations exercise existing real application components. Existing cinema/sports seeds are preserved. A successful repeated seed does not recreate listings, sessions, forms or reset capacity.

Deployed verification uses the existing demo operator's real Mailpit OTP/session and the actual local API/database. Four free demo orders were accepted, confirmed, issued QR tickets, fully cancelled and checked for restored capacity. These are labeled local verification records, not real customers/revenue/provider charges or admissions. The script logs no OTP, cookie or QR credentials. Evidence: events-deployed-booking.json. Browser verification is blocked by unavailable browser host.

Remaining event scope: recurrence generation/exceptions, phased categories/packages, multi-day passes, authorized online access, disruption remedies and paid refunds. Existing live Razorpay integration is still unconfigured; no live or provider Test Mode payment is claimed. This completes upcoming discovery plus the demonstrated core single-session journey, not every detailed event requirement.
