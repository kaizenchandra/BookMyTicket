# ADR 061: Durable listing submission retries

FE:CAT-05/08, BE:CAT-04/07 and BE:API-03 require recoverable listing transitions. A lost successful submission response previously caused a stale-version conflict on retry. Migration 054 adds immutable Catalog submissions keyed by listing/input version, with actor, resulting version, original result and database timestamp. The business key is durable and independent of transient HTTP retry-key retention.

The existing submission transaction locks the listing and checks current writable membership through Providers' public contract. An existing record returns its original result only to its original actor; another actor conflicts. Membership downgrade/revocation blocks replay. New submissions still require approved provider state, an editable draft/changes-requested listing and the expected current version. Requests now bound version values before SQL.

For a new command, pre-change revision, submitted state and immutable original result commit atomically. Identical concurrent requests serialize to one transition and one revision. Historical replay performs no writes and skips new-transition approval checks: later provider suspension, listing review, resubmission or publication cannot be reversed by replaying an earlier result. The original response may describe an earlier state; current state must be refreshed separately. Legacy submissions without durable records retain their former stale-version behavior, with no fabricated backfill.

The shared catalog submission UI captures listing ID/version before submitting. After a failure, Retry original submission resends exactly that version; Dismiss retry clears the local attempt. Success clears the attempt and refreshes current review state with wording that does not assert the historical result is still current. Session changes clear local recovery state. Recovery is in memory and does not survive browser closure; broader unsaved-form navigation acceptance remains open.

Tests cover six concurrent identical submissions, one revision/record, changed actor and invalid-state/version conflicts, correction/resubmission/publication followed by old replay, provider suspension, membership downgrade/revocation and immutable rows. Full native/Docker suites exercise existing category publication/booking flows with the new persistence. Browser retry/accessibility, retention approval and generic draft-save replay remain open.
