# ADR 101: Customer administration through owner-module read ports

Identity orchestrates the customer directory and detail workspace through shared structural ports. Profiles owns profile names and consent-aware saved-attendee decryption; Bookings owns activity cohorts and order history; Payments owns capture/attempt/recovery observations; Support owns case summaries. No adapter reads another module's private tables. Read projections use a repeatable-read transaction and audit the actor, customer and history kind without search contacts or private content.

Customers are identity accounts, including accounts that also hold staff roles. `customers.read` plus current MFA authorizes masked customer views. Histories additionally require `bookings.read`, `finance` or `support`. Status/flag changes additionally require `access.manage` inside the mutation transaction. Existing account mutation serialization, self-change/last-manager checks, expectedVersion, session revocation and atomic before/after audit are reused. The customer mutation schema admits no roles, grants, contact edits or verification overrides. Flags are explicit administrative annotations, not computed risk scores.

Directory registration and booking-creation windows are independent inclusive-start/exclusive-end timestamps. Activity filters run before pagination; displayed activity totals are all-time. “Confirmed” counts recorded confirmation, including subsequently cancelled orders. Date/UUID keysets bind actor and filters. Histories omit snapshots, raw provider identifiers and support subjects/messages. Payment observations are event history, not additive revenue or a refund ledger.

Migration 075 adds contact verification time and constrained customer flags plus a booking-owner index. Existing contacts are not declared unverified: consumed OTP evidence is labelled historical verification without a fabricated timestamp; missing evidence is labelled not recorded. Successful future OTP verification supplies the timestamp. Saved attendees require latest granted consent and are masked before leaving Profiles; absent keys/corrupt ciphertext return unavailable. Wallet and loyalty remain explicitly unsupported.

Cross-module activity/name matches currently materialize matching IDs inside one database transaction. This preserves module ownership and filter-before-limit correctness, but needs load testing and a dedicated reporting projection before large-scale deployment. No external services, new grants, dependencies or production deployment are introduced. Browser acceptance is outstanding; build, HTTP/database and container verification are separate evidence.
