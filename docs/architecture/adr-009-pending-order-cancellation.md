# ADR 009 — Cancel an unconfirmed order without inventing refund policy

Purchased commercial snapshots currently contain cancellation prose, not machine-readable deduction/deadline/resale rules. This slice therefore cancels only orders in `pending_payment`. It does not interpret free text as a refund policy or enable cancellation of confirmed entitlements. Full/partial confirmed-ticket cancellation and provider refund execution remain required follow-up work.

Bookings owns a two-minute, owner-bound preview and cancellation command/result records. The preview states that cancellation releases the hold and prevents fulfillment but neither stops an external bank transaction nor proves a completed refund. Refund amount is null, never a fabricated zero or promised payout. Payment activity is read through a Payments contract; if activity starts after a no-activity preview, the user must review a new preview. Repeated preview retrieval does not extend an unexpired preview. The compact preview table keeps one row per order; superseded preview IDs are invalid.

Confirmation locks an actor command key, then the owned order. Identical keys return the recorded outcome; changed input conflicts. Order state and preview expiry/payment activity are rechecked inside the transaction. Inventory locks sorted occurrences and the original reservation, releases only unconsumed holds and clears seat ownership only where the old reservation still owns it. Bookings cancellation, inventory release, command result, audit and durable outbox event commit together. A consumed reservation rejects the whole transaction. No external request occurs while locks are held.

Payment preparation and trusted capture confirmation also lock the order, so capture versus cancellation has one winner. If confirmation wins, pending cancellation is rejected. If cancellation wins, a later capture cannot fulfill or resurrect the order; the existing Payments recovery obligation and balanced customer-refund-liability journal are recorded. The booking remains cancelled independently of payment recovery. Razorpay order creation that returns after a cancellation rechecks order state before returning new checkout details. This cannot retract a checkout already opened or prevent an in-flight bank charge.

Customer UI provides explicit review, reason, acknowledgment, retry handling, current status and genuine recovery-record information. It never calls a cancellation a completed refund. Operational refund execution, notifications, richer policy-based cancellation and retention of cancellation metadata remain incomplete. No live charge/refund or provider Test Mode evidence is claimed.

Tests cover duplicate commands, changed input, ownership, expired preview, new payment activity, released capacity, stale seat ownership, capture races, late capture deduplication, payment preparation rejection, consumed-hold rollback and authenticated HTTP behavior. Browser acceptance is separate.
