# ADR 063: Idempotent generic listing creation

FE:CAT-01/08 and BE:API-08/09/12 require retry-safe creation. POST /api/v1/organizations/:id/listings now requires an Idempotency-Key of 8–100 characters, matching category command key bounds. The browser and known test callers are updated, and OpenAPI marks the header required. Callers without it receive 422; previous unkeyed creations cannot be reconstructed.

Migration 056 adds immutable catalog.creations, keyed by actor/organization/operation key and uniquely mapped to the created listing. The operation is scoped by its dedicated table. Creation runs in a local transaction: current writable membership is held under the Providers contract, an advisory transaction lock serializes the key scope, and existing normalized input is compared using JSONB equality. Identical requests return the original result; changed content conflicts. Another actor or organization has an independent scope.

The listing and durable input/result mapping commit atomically. A failed mapping insert rolls back the listing. Durable mappings have no automatic expiry; business uniqueness is retained. Original replay requires current access, performs no listing writes and can describe a state preceding later edits/review/publication. New deliberate creation requires a new key. Metadata object order and existing transport text normalization do not create false conflicts.

The frontend generates one UUID key per new creation attempt and retains the exact body/key after failure. It blocks changed new-listing content until the outstanding attempt is resolved or explicitly cleared. Retry original creation reuses the payload; if the form has changed, it asks before resetting those edits. Clearing recovery also requires confirming that current listings were checked. Fields disable during saves. Session changes clear local recovery state. Successful recovery refreshes current listings and displays the recovered reference.

Tests cover six concurrent identical requests creating one listing, required/bounded keys, normalized/key-order equality, changed-payload conflicts, actor/organization isolation, replay after edits and publication, current membership downgrade/revocation, immutable mapping and rollback after a failed durable insert. Existing authorization and publication tests supply required keys. Browser recovery/confirmation/accessibility, browser-close key persistence and approved retention policy remain open.
